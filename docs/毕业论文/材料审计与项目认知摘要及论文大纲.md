# 第一部分 材料审计与项目认知摘要

## 1. 审计结论

当前仓库已经具备撰写软件工程类本科毕业论文主体内容的基础。项目不是单一页面或单次大模型接口调用，而是由移动端、Web 端、Java 业务后端、Python 智能体服务、MySQL 数据库及容器化部署链路组成的多服务系统。活动预约、申请审核、订单交流、校园动态、媒体上传、评论点赞、用户资料、后台治理、智能体工具调用、写操作确认、长期记忆和部署验证均能在源码中找到对应实现。

现有材料足以安全撰写绪论、相关技术、可行性分析、需求分析、系统设计、主要功能实现和部分系统测试内容。论文的重点宜落在“校园活动任务链路与可控多智能体协同机制”上，而不是堆叠框架名称。

目前仍不适合直接宣称论文已经完全成稿，主要原因如下：未提供参考论文或学校格式模板；数据库 SQL 文档与当前 JPA 实体存在版本漂移；真实界面截图数量不足；后端自动化测试和性能测试证据不足；普通接口仍未形成生产级身份认证；仓库配置中存在敏感凭据暴露风险。这些问题应在论文正式写作和答辩材料整理前处理。

## 4. 已确认技术栈

### 4.1 前端与移动端

- Web 端：Vue 3、Vue Router、Pinia、Axios、Element Plus、Sass、Vite。
- 移动端：uni-app、Vue 3、Vuex、Vite、HBuilderX/Android 打包链路。
- 通信方式：RESTful HTTP、文件上传、SSE 渐进式事件与文本返回。
- 交互形态：用户端 Web、移动端 H5/App、Web 管理后台。

### 4.2 后端与数据层

- Java 21、Spring Boot 4.0.0、Spring MVC、Spring Data JPA、Spring Validation、Spring Security、Spring Mail。
- MySQL 8 持久化；开发配置采用 JPA `ddl-auto=update`。
- BCrypt 用于密码和验证码摘要校验。
- 统一 API 前缀为 `/api/v1`，后端审计识别出 9 个 REST Controller 和 77 个映射接口。
- 文件系统保存头像、图片和视频，Nginx/后端提供上传资源访问链路。

### 4.3 智能体与外部能力

- FastAPI 0.115、LangChain 0.3、LangGraph 0.3、langchain-openai、httpx、sse-starlette。
- 通过 SiliconFlow 的 OpenAI 兼容接口调用 Qwen 系列模型；主模型和路由模型可分别配置。
- 使用 LangGraph 预构建的 ReAct Agent，而非自定义完整 StateGraph。
- 高德地图 MCP 提供地点检索、周边检索、天气、地理编码、步行路线和驾车路线。
- 代码中共有 27 个 `@tool`：24 个领域/实用工具和 3 个主智能体委派工具。

### 4.4 部署与持续集成

- Docker、Docker Compose、Nginx、GitHub Actions。
- 本地构建镜像并打包为 tar，再上传服务器加载，适用于服务器公网拉取镜像不稳定的环境。
- 生产编排包括 MySQL、智能体服务、Java 后端和 Web/Nginx 服务。
- 提供版本标签、前一版本记录、回滚脚本、内外网 smoke test。

## 5. 已确认核心模块与任务链路

### 5.1 用户与身份模块

- 邮箱验证码注册、密码登录、退出、忘记密码、修改密码。
- 用户资料查询、昵称/头像/签名更新、用户搜索、公开用户主页。
- BCrypt 已用于密码存储和验证码匹配。
- 当前登录令牌和刷新令牌仍为 mock token；普通业务接口主要依赖客户端传入的 `X-User-Id`，不能表述为已经完成 JWT 认证。

### 5.2 活动预约模块

- 活动创建、分页浏览、按状态/校区/活动类型/时间等条件筛选、详情查询、编辑、取消和完成。
- 活动字段包含活动类型、性别要求、校区、地点、开始时间、备注、人数上限、当前人数和状态。
- 参与者可以申请和撤销申请；发布者可以查看申请、通过或拒绝申请，并接受参与者。
- 订单内支持消息交流和引用回复。
- 活动状态包含待匹配、进行中、已完成、已取消和已过期；申请状态包含待审核、已通过、已拒绝和已撤销。

### 5.3 校园动态模块

- 发布、查询、搜索、编辑和软删除动态。
- 动态可以关联活动订单，可上传图片或视频。
- 评论与子评论复用统一内容实体，通过父级关系形成递归评论树。
- 点赞采用独立关联实体，并通过用户与内容唯一关系避免重复记录。
- 内容状态支持正常、待审核、拒绝和删除，可由系统设置控制新内容初始状态。

### 5.4 AI 助手模块

- 主智能体负责意图分析、任务拆解和子智能体调度；订单、社交、地图天气三个领域子智能体负责受限工具集。
- 路由由缓存、上下文捷径、确定性读写规则、轻量模型、主模型复核和故障降级共同组成。
- 读任务可直接执行；写任务先形成结构化确认草稿；混合任务先查询，再根据用户选择形成草稿，最终确认后执行。
- 写操作确认不仅依赖 Prompt，还由业务代码门控，并保留 `actionKind` 防止确认后执行到错误领域。
- 支持地图候选、订单结果、动态结果和用户结果的结构化 Artifact，以及“第一个”“第二个”“指定名称”等上下文选择。
- 支持会话持久化、消息持久化、显式记忆管理和隐式长期记忆提取过滤。
- SSE 会实时传递意图、执行步骤、确认请求、Artifact、记忆提交、错误和完成事件；最终文本目前是在智能体执行完成后分块发送，不应描述为底层模型逐 Token 流式推理。

### 5.5 管理与治理模块

- 用户类型和状态管理、活动管理、申请管理、内容/评论审核和删除。
- 文件资源管理、AI 会话与长期记忆审计、系统设置、操作日志和统计仪表盘。
- 管理接口通过拦截器校验 `X-User-Id` 对应用户是否为管理员，但仍受当前身份标识机制边界影响。

## 6. 数据库与接口事实

### 6.1 当前实体体系

当前后端共有 14 个 JPA 实体：

1. 用户与验证：用户、验证码记录。
2. 活动协作：活动订单、活动申请、订单接受记录、订单消息。
3. 内容互动：动态/评论、媒体、点赞。
4. 智能助手：AI 会话、AI 消息、AI 长期记忆。
5. 管理治理：管理员审计日志、系统设置。

论文数据库设计应根据这些实体和实际数据库快照重新生成，不应直接复制旧版 `数据库.sql`。

### 6.2 主要关系

- 一个用户可发布多个活动、提交多个活动申请、发送多条订单消息和发布多条内容。
- 一个活动可有多个申请和消息，但接受记录被设计为活动的一对一关系。
- 动态和评论共用内容实体，评论通过父内容形成树形关系；动态可以选择性关联活动。
- 内容与媒体为一对多关系，用户与内容通过点赞实体形成多对多语义。
- 用户与 AI 会话、AI 记忆为一对多关系；AI 会话与 AI 消息为一对多关系。

### 6.3 接口边界

| 接口域 | 基础路径 | 主要职责 |
| --- | --- | --- |
| 认证 | `/api/v1/auth` | 登录、注册、退出、刷新、找回密码 |
| 验证码 | `/api/v1/verify` | 邮箱验证码发送 |
| 用户 | `/api/v1/users` | 资料、头像、密码、用户搜索 |
| 活动 | `/api/v1/orders` | 活动、申请、审核、接受、消息、状态转换 |
| 内容 | `/api/v1/contents` | 动态、媒体、评论、点赞、搜索 |
| 上传 | `/api/v1/upload` | 图片、视频和资源删除 |
| AI | `/api/v1/agent` | 会话、消息、SSE、长期记忆 |
| 管理 | `/api/v1/admin` | 用户、活动、内容、文件、AI、设置和审计 |
| 系统 | `/api/v1/system` | 公共系统设置和维护信息 |

## 7. 参考模板学习结果

### 7.1 模板可用性

当前项目目录未发现用户所述的参考论文 PDF、DOC 或 DOCX，也未发现学校论文格式模板。`素材` 目录中的 Vue 后台管理模板属于界面开发素材，不属于论文结构范文，不能用于学习摘要、章节、题注或参考文献格式。

### 7.2 当前采用的临时结构策略

在参考论文缺失的情况下，大纲暂采用中国本科软件工程“设计与实现”类论文常见的八章结构：绪论、相关技术、可行性分析、需求分析、系统设计、系统实现、系统测试、总结与展望。需求、设计和实现分章处理，每章设置本章总结；图题和表题暂采用“图 章号-序号”“表 章号-序号”。

### 7.3 待补充后需要重新学习的内容

- 学校是否要求独立“可行性分析”章节。
- 摘要字数、关键词数量、英文摘要格式。
- 标题编号、字体字号、行距、页边距、页眉页脚和目录格式。
- 图表题注位置、参考文献著录标准和致谢格式。
- 参考论文的章节密度、图表密度、测试用例表格式和本章总结习惯。

参考论文补充后，应只迁移结构和写作习惯，不得迁移其业务模块、数据库、算法结果、测试数据或参考文献。

## 10. 项目认知摘要

CampusHub 面向校园活动信息分散、参与链路割裂和活动后内容沉淀不足的问题，将“发现活动—申请参与—发布者审核—活动交流—完成活动—发布动态”组织为可追踪的任务链路。系统同时提供 Web、移动端和管理端，Java 后端负责业务规则、持久化和文件资源，Python 智能体通过 REST 工具复用后端能力，不直接操作数据库。

项目的主要技术工作不在于训练新模型，而在于把通用大模型约束为可用于真实业务的多智能体协作层。主智能体只持有三个领域委派工具，子智能体分别处理活动、社交和地图天气任务；高频只读任务由确定性路径直接执行，复杂语义由模型辅助判断，写操作则必须经过结构化草稿和用户确认。系统通过 `actionKind`、允许委派列表、委派次数限制、递归限制、任务复用、路由降级和上下文 Artifact 恢复，降低误操作、跨领域漂移和循环调用风险。

因此，论文的主要工作量可以概括为：构建多端校园活动协作平台；设计活动与内容的关联数据模型和状态机制；实现面向真实业务接口的多智能体工具调用；建立读写分级与确认执行机制；通过结构化 SSE 事件提高执行过程可观察性；使用多组场景回归测试验证智能体路由、上下文与安全边界。
